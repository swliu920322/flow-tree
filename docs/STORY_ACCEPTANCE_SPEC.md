# Flowtree 用户故事、验收执行与流程可视化规范

版本：0.1（讨论草案）  
整理日期：2026-11-08  
适用范围：已有项目的故事梳理、测试补充、验收执行、最小代码修复与进度展示。

本文记录本轮产品讨论，为后续完善提供共同依据，不表示相关能力已经实现。文中的字段结构和状态名称是初版建议，正式实现前可继续调整。

## 1. 已确定的方向

1. 从用户在客户端的真实使用流程出发，描述用户目标、操作和可观察结果，再关联后端逻辑验证。
2. Flowtree 应读取项目文档，提取故事草稿、发现规则空白，逐步生成测试与验收页面。
3. 默认展示正常流程，沿自上而下的瀑布顺序阅读；异常、边界及恢复场景通过节点旁的 `+` 展开。
4. 稳定 ID 用于追溯、关联和执行，不以横向 ID 树作为默认阅读方式。
5. 保留逻辑检查、测试生成、代码完善、进度与可视化能力；代码完善围绕明确验收条件进行，避免扩大成自主重构平台。
6. 第一阶段聚焦编码层。业务数据库表设计、迁移和实际数据管理由项目自身负责，预留适配入口。
7. CLI、MCP、Web 共用同一套故事、执行与证据模型，结果含义保持一致。

## 2. 产品定位与边界

Flowtree 是面向已有项目的故事驱动验收与改进工具。核心闭环为：

> 项目文档 → 故事与规则草稿 → 规则确认 → 测试映射与补充 → 实际执行 → 缺陷与最小修复 → 回归证据 → 流程展示与人工验收。

| 能力 | 第一阶段负责范围 | 范围之外 |
|---|---|---|
| 文档理解 | 提取故事、标注来源、识别过时信息及规则冲突 | 把历史文档全部视为当前事实 |
| 逻辑检查 | 对照实现检查状态、权限、边界和不变量 | 自行决定未定义的产品规则 |
| 测试 | 关联已有测试、补充缺口、运行并保存证据 | 用占位结果或接口 200 代替业务断言 |
| 代码完善 | 修复有明确验收依据的实现缺陷 | 无验收依据的架构重写、功能扩张 |
| 数据库 | 调用项目提供的隔离测试环境和数据夹具 | 通用建表、ORM、迁移及生产数据管理平台 |
| 可视化 | 展示流程、分支、实现情况、验证证据及人工验收 | 根据生成节点数量推断真实完成率 |

建议让 Flowtree 负责规范、执行编排、证据与展示，由外部编码 Agent 完成分析、测试和补丁。第一阶段不必自建完整 AI 编码运行平台。

## 3. 故事的三个层次

| 层次 | 必须回答的问题 | 示例 |
|---|---|---|
| 用户故事 | 谁为了什么目标做什么 | 已登录用户希望记录一次克制消费 |
| 主流程 | 用户如何一步步完成目标 | 打开弹窗 → 输入 → 提交 → 查看结果 → 重新进入 |
| 验收场景 | 在哪些条件下，应得到什么可判断的结果 | 输入 0.25 后进度增加 0.25，A/B 积分保持不变 |

故事表达业务契约。接口、函数、表和测试文件放在独立技术映射中，避免故事跟随当前实现缺陷反向变化。

## 4. 文档格式建议

建议采用 Markdown 说明配合 YAML 结构化故事：Markdown 解释背景和决策，YAML 提供可校验和可执行的字段。第一版不要求用户维护多种等价格式。

必要信息包括：稳定 ID、标题、执行人、目标、来源、初始条件、输入、主流程、分支、跨步骤不变量和待确认问题。

以下示例仅说明格式，数值作为隔离测试夹具，不代表读取用户真实数据。

```yaml
schema_version: "0.1"
id: SAV-001
title: 记录一次克制消费
actor: 已登录用户
goal: 记录忍住的消费并查看累计挑战进度
sources:
  - path: USER_STORY_MAP.md
    anchor: US-38
preconditions:
  - 用户已建立储蓄挑战
  - 当前挑战进度为 10.00
  - 当前 A 积分为 20.00
inputs:
  category: 数码消费
  amount: "0.25"
main_flow:
  - id: STEP-01
    action: 用户打开克制记录弹窗
    expected:
      - 可输入分类、金额和备注
  - id: STEP-02
    action: 用户选择分类，输入金额并确认提交
    expected:
      - 提交期间显示处理状态
  - id: STEP-03
    action: 用户查看提交结果
    expected:
      - 挑战进度为 10.25
      - 新增且仅新增一条金额为 0.25 的克制记录
      - 成功提示显示 0.25
      - A 积分仍为 20.00
  - id: STEP-04
    action: 用户离开页面后重新进入
    expected:
      - 进度与记录保持一致
branches:
  - id: CASE-01
    at: STEP-02
    kind: validation
    condition: 金额为 0
    expected:
      - 明确提示金额无效
      - 进度和记录不变
    continuation:
      type: end
  - id: CASE-02
    at: STEP-02
    kind: recovery
    condition: 服务端处理成功但客户端未收到响应
    expected:
      - 保留原操作标识，重试确认原操作结果
      - 不重复增加进度或记录
    continuation:
      type: rejoin
      target: STEP-03
invariants:
  - 挑战记录不改变 A/B 积分
  - 用户只能操作自己的挑战
  - 金额最多两位小数
open_questions: []
```

### 格式与内容校验

- 故事 ID 在项目中唯一，步骤和场景 ID 在故事内唯一；跨故事引用使用完整限定 ID。
- `at` 和回归目标必须存在；重命名标题不改变 ID，删除或替换须保留追溯关系。
- 金额使用十进制字符串，时间边界明确时区和测试时间，避免依赖运行当日或二进制浮点近似。
- 初始条件和输入足以让测试重复执行；“显示正常”“功能正确”不能单独作为通过标准。
- `open_questions` 不为空时，相关验收项保持待定；明确的其他场景仍可继续执行。
- 分支不要求穷举所有组合，但应检查输入边界、权限、状态、重复操作、并发、时间、持久化和失败恢复是否适用。未覆盖与不适用必须区分。
- 新增需求与既有规则冲突时先列出差异，不为让测试通过而自动削弱验收条件。

## 5. 流程与分支语义

默认主流程按用户可理解的操作顺序自上而下排列。后端事务细节在节点详情展开，保持用户路径可读。

分支的出口可为：

| 出口 | 含义 | 示例 |
|---|---|---|
| `end` | 本次操作结束 | 非法金额被拒绝，数据保持不变 |
| `rejoin` | 处理后回归主流程 | 确认丢失响应的原请求结果后进入结果页 |
| `retry` | 返回指定步骤重新操作 | 修正输入后再次提交 |

`retry` 可作为后续字段扩展，须定义目标和有限执行策略；恢复场景不得无限循环。

“异常场景”与“测试失败”含义不同：错误输入得到正确拒绝，场景应判通过。驳回、重提、退款和恢复等有业务后续的分支，必须能表达返回或汇合。

用户流程可能存在返回环；任务依赖图仍要求无环。两种关系分别建模，不把用户的重试边直接放进开发依赖 DAG，也不为了画成无交叉图而删除真实业务关系。

## 6. 可视化约定

1. 默认只展开正常主流程，采用纵向瀑布布局，优先展示用户动作、预期结果和当前状态。
2. 每个有分支的节点旁显示 `+` 与分支数量；点击后在局部展开边界、异常和恢复场景，再次点击收起。
3. 收起仅改变展示：节点上仍显示失败、待定和未执行分支数量，不能把问题藏进折叠区域。
4. 默认不突出 ID；在详情、复制链接、测试报告和技术视图中可查看稳定 ID。
5. 节点详情依次展示业务规则、关联实现、测试列表、最近执行证据和人工验收记录。
6. 额外提供“仅看失败/未覆盖”“全部分支”入口，便于测试人员核对完整性。
7. 颜色配合文字或图标表达状态，自动验证与人工签字分别展示，不能仅靠绿灯代表全部完成。

默认展示示意：

```text
打开记录弹窗
      ↓
填写并提交金额       [+ 3 个边界/恢复场景 · 1 个未执行]
      ↓
查看进度与记录       [+ 2 个隔离/一致性场景]
      ↓
重新进入确认持久化
```

## 7. 从故事到真实测试

每条验收场景应关联验证层级和真实测试入口。一个场景允许映射多个测试，同一测试也可验证多个规则，但关联关系须能检查实际断言。

| 验证层级 | 可证明的内容 | 不能替代的内容 |
|---|---|---|
| 代码检查 | 发现疑点、定位实现与规则差异 | 运行时正确性 |
| 后端测试 | 权限、状态、事务、不变量和接口契约 | 客户端入口与交互可达性 |
| 客户端测试 | 输入、展示、状态、交互与请求行为 | 正式设备、部署网络和真实持久化环境 |
| 联调/设备验收 | 真实环境中的完整旅程 | 未执行的其他分支 |

执行顺序建议：先映射已有测试 → 找缺口 → 生成补充测试草稿 → 检查断言及隔离性 → 实际运行 → 解析结果 → 关联证据。生成测试文件本身不产生“通过”状态。

占位脚本、固定 `passed = True`、零测试、缺少测试、超时、解析失败及全部跳过均不能判通过。未知结果保留为未知，执行错误与产品断言失败分别记录。

每批执行至少保留：运行 ID、故事版本、代码 Commit、工作区是否有修改、测试入口、环境标识、开始时间、结果计数和原始报告位置。工作区有修改时，补充源码快照或差异摘要以便识别实际基线；不得冒充该 Commit 的干净验证。

历史结果按原版本保存，代码或验收条件变化后标记证据待更新，不删除旧记录，也不直接沿用为当前通过。完整有效性计算可后续细化。

## 8. 最小代码完善规则

允许围绕明确验收条件补校验、修权限、修状态流转、修展示及必要的局部调整。每个补丁须说明：对应规则、复现方法、修改内容和回归结果。

涉及新增业务规则、数据结构变更、对外契约变更或大范围重构时，先形成可审阅的变更建议，不自动扩大本次修复范围。规则不明确时先保留待定，不让 Agent 自行发明预期。

原则：能指出满足哪条验收条件，能证明修改前后的行为差异，修改规模与问题匹配。不能通过删除场景、弱化断言或伪造终审来获得通过。

## 9. 数据库及外部环境适配边界

第一版优先复用项目已有测试命令和夹具，允许项目提供准备、运行及清理入口。适配器的最小职责为：

- 声明验证所需环境与隔离范围。
- 准备测试数据并提供场景所需标识。
- 执行项目已有测试或受控测试入口。
- 返回可解析结果与报告位置，并清理本次测试数据。

Flowtree 不代替用户设计业务表、自动迁移或处理真实资金/生产数据。环境未配置时，依赖该环境的场景标为未执行或环境阻塞；仍可运行不依赖它的编码层测试。

业务数据库适配与 Flowtree 自身保存故事、运行记录的存储方式分开。第一阶段无需设计通用数据库抽象框架。

## 10. 进度与验收状态

分别记录以下维度，不用单一百分比混合表达：

- 规则定义：草稿、待确认、已确认。
- 实现情况：待检查、缺失、已有实现、发现缺陷。
- 自动验证：未映射测试、未执行、执行中、通过、失败、环境阻塞、证据待更新。
- 人工验收：未验收、通过、驳回、不适用。

实现情况是检查结论；自动验证状态来自真实执行；人工签字来自真实用户操作。Agent 自动验证通过只更新自动验证维度。

模块汇总应展示分母，如“已定义 12 个场景，9 个有测试，7 个本次通过，2 个失败，3 个未执行”。主流程全通过但必需分支未完成时，不显示整条故事完全验收。被前置条件阻断的步骤不能报为已执行。

## 11. 与当前代码及历史规范的关系

现有设计中的双阶段验收、透镜与电路图可以保留。本文补充用户故事、分支语义、证据及最小修复边界；默认展示从横向任务树调整为纵向用户流程，不要求取消技术拓扑视图。

旧文档中“AI 不生成代码”的绝对边界，后续需与本文的“外部 Agent 依据明确验收条件辅助最小修复”统一。本文不直接变更现有 API、状态枚举或存储结构；实现迁移应另行规划。

2026-11-08 只读检查观察：

- CLI 扫描器查找文档路径，生成器按项目名称选择固定模板，尚未按文档内容生成故事和测试。
- 通用和 Piggy 验收脚本存在固定成功结果，不能作为真实验证证据。
- 模板预填部分通过状态及人工签字，须与演示数据明确区分。
- CLI 失败状态 `blocked` 与后端 `review_reject` 尚未统一。
- MCP 文件有工具函数，主入口尚未实现完整协议接收与分发。

这些是后续实施输入，不表示本轮已经修复。

## 12. 下一轮完善建议

1. 用三个真实故事校验格式：单人任务完成、家庭任务驳回重提、克制记录响应丢失后重试。
2. 统一故事 Schema 与引用校验，定义哪些规则需要人工确认。
3. 接入现有 pytest/Flutter 结果，消除占位成功，建立可追溯执行记录。
4. 实现纵向主流程与 `+` 分支展开，验证折叠后仍能看到风险摘要。
5. 再接入最小补丁协作和三种入口；数据库适配复用已有测试体系，逐步扩展。

尚待讨论：故事文件目录约定、最终字段名称、状态与旧数据迁移、证据有效性算法、Agent 补丁的配置方式，以及人工验收的身份与权限机制。

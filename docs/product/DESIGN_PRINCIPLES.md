# 架构原则（项目负责人已确认）

日期：2026-11-12。确认人：项目负责人（本次会话中明确答复"这三个原则我确认是好的"）。记录人：Claude。

## 已确认的三条原则

1. **项目自己的东西跟着项目走。** 需求（用户故事原文）、测试、规则确认与人工验收记录，归被验收的第三方项目，与它的代码一起变化、一起版本化。
2. **引擎不认识具体项目，是通用的。** FlowTree 引擎只认识契约（故事、映射、证据的格式），不为某个具体项目写特例；新增一种测试框架靠运行器适配器，不改核心。
3. **命令行（CLI）是权威。** 网页、MCP 等只是它的外壳，不自带判断逻辑；有效性、聚合与闸门的结论只有一份，由同一个核心产生。

## 这三条的边界（避免过度解读）

- 只确认了原则，**没有确认具体设计**：文件放在项目的哪个目录、本机配置如何拆分、证据存放位置、CI 如何接入、人工签字记录的格式，都还没有决定，也没有人在等这个答案。
- 没有要求现在迁移任何文件。当前 US-23 / US-24 的验收工作不受影响，仍按现有目录和配置进行。
- 原则 1 的理解：需求原文由项目负责人定义；我们的 yaml 是对原文的**可测试细化**（`sources` 指回原文），由智能体起草、负责人确认。它不是需求本身。
- 原则 3 不直接决定本地与 CI 的优先级。证据能否复用取决于输入、运行时与执行上下文是否匹配；不能仅凭“来自本地/CI”判断有效性。“CI 作权威、本地作参考”属于尚未决定的发布闸门策略，不由这条原则推出。
- CLI 是标准执行与核对入口；唯一判定来自共享核心服务。Web/MCP 可以调用同一核心，不要求绕道启动 CLI 子进程，也不能各写一套结论。
- 验证引擎必须能在没有大模型的情况下执行测试、读取证据及计算状态。AI 起草与修复是可选的编排环节，可以接入模型调用；产品提供用户配置 API key 的接入方式，也允许用户在自己的终端使用 Claude Code 等外部 AI。密钥属于本机敏感信息，不入版本管理，验证引擎不依赖密钥。不得把“验证引擎不依赖模型”扩大解释成“产品不能提供 AI 功能”。（2026-11-14 依据负责人经 Claude 转来的最新决定补充；具体提供方与密钥读取方式待设计。）

## 2026-11-13 补充：负责人明确的产品方向

来源：负责人在本次会话重述最初设想，并要求将能确定的原则持续补入文档。以下记录产品目标与边界，不表示对应功能已经实现，也不把 Claude 的建议自动升级为决定。

1. **围绕完整使用流程，减少用户操心。** 目标链路是：接入项目、配置所选 AI → 根据需求原文起草故事 YAML、测试计划和人工验收指引 → 生成或补强测试并执行逻辑验收 → 用户按指引操作、最好在页面反馈 → 本轮结束汇总意见 → 用户或所选 AI 修改并进入下一轮。近期的轮次、发现记录设计应服务这条流程，不先扩展为复杂管理系统。
2. **逻辑验收和人工验收分别呈现。** 逻辑进度与卡点来自故事、映射和执行证据；人工待操作不降低逻辑验收的完成状态，也不能被显示成人工通过。页面不应以一个“整体未完成”混淆两者。人工反馈若发现业务问题，作为发现登记，再影响相关处理；不因其来自人工而忽略问题。
3. **用户可选择谁来完善测试和修复代码。** 验证引擎提供证据和问题；用户可以调用产品接入的 AI，也可以使用自己的 AI 或自行修改。“工具不改被测代码”应收窄为验证引擎的职责边界，不能禁止用户授权的独立修复环节。生成或修改后重新验证，代码、故事等输入变化沿用现有指纹失效机制。
4. **按轮次整理反馈和修改。** 支持用户走完本轮后集中汇总意见、再安排修改，避免把不同版本的结果拼成一次通过。具体开始/结束机制、中途变更处理和记录格式尚未确定；本条不构成禁止紧急修复的规则。
5. **项目材料归项目，产品只提供通用能力。** 延续前三条原则：需求、故事细化、映射、指引、测试及验收记录应跟随被测项目；具体目录、哪些产物入库、哪些包含敏感信息及迁移方式尚未确定。不据此直接把证据、缓存或本机密钥全部加入版本管理。

## 文档如何随设计更新

- 现行原则与设计允许持续修订，记录来源、日期、确认状态及被替代的表述；不以历史文档阻止负责人后来明确的方向。
- 明确区分：负责人决定、评审建议、待决设计、当前实现。提案、自测通过或 AI 相互认可，不等于负责人已确认。
- 现行规范更新时核对相关文档和实际入口，避免两份互相冲突的“当前规则”；带日期的交付与验收记录保留当时事实，用后续状态链接说明，不改写历史结论。

- 人工与规则记录格式、权限、轮次聚合、CI 和发布策略。此前讨论仍是提议，没有因本次补充自动生效。

## 2026-11-14 决定补充（依据负责人经 Claude 转述的最新回答）

- **规则确认是起草到正式验收流程的必经点。** AI 可以先产出草稿，不需要用户在生成前反复审批；未经确认的内容保持“未确认”，不能声称其代表已确认需求。格式校验或测试通过不等于规则确认。用户可能不认真确认，产品应减少误确认和误读，具体交互另行设计。
- **AI 接入方式明确。** 用户可在产品配置中提供 API key 接入模型，也可使用自己终端中的 Claude Code；不强制模型来源。密钥不入版本管理；具体保存、引用、检查与日志处理仍须设计。
- **开发优先方向明确。** 先打通项目初始化、AI 配置与调用的核心链路，页面反馈和本轮汇总排在后面。本条不等于确认只接 Anthropic、具体目录布局，或授权发起收费模型调用。

## 2026-11-14 决定补充：独立命令与首个提供方

来源：负责人本次直接提出“电路图应该在逻辑验收测试之后生成”“每一个步骤拆成独立的启动命令”，并选择 DeepSeek、优先通过 API 地址配置通用化，必要时再加适配器。

- **步骤可独立启动。** 初始化、AI 连通检查、故事起草、计划/校验、测试生成与执行、结果图展示应具有清晰的调用边界。初始化不隐式生成电路结果图、调用模型或触发同步。具体命令名及旧 init 的兼容/退役方式仍待提案明确，本次不改旧命令。
- **结果图在逻辑验收执行后形成。** 依据本次真实执行证据展示通过、失败及尚未验证的范围；不要求全部通过才显示图。执行前的故事或计划预览不得冒充逻辑验收结果。图的具体实现与是否沿用“电路图”名称另议，不意味着恢复旧固定模板。
- **首个提供方选 DeepSeek。** 优先实现可配置协议、API 基地址/请求路径、模型和密钥环境变量引用的通用调用边界；协议不兼容时才增加适配器。仅修改 URL 不能保证任意模型协议兼容。具体配置结构待评审，不在核心写死提供方或模型名称，不绑定付费控制台订阅。本次没有授权实际付费调用。

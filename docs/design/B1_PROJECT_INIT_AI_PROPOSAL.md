## 3. 目录与入库规则（被测项目内）

```
<project>/.flowtree/
  flowtree.yaml      可入库  可移植配置：路径、测试命令；不含 AI 地址与密钥变量名
  stories/ mappings/ guides/ drafts/   可入库（drafts 为草稿，验证引擎不读取）
  local.yaml         应忽略  本机非敏感覆盖（解释器路径等）
  runs/ cache/ evidence/               应忽略  运行产物（证据是否入库另议）
  .gitignore         由 init 在不存在时创建；已存在则不修改
```

- 不改项目根 `.gitignore`，不整体忽略 `.flowtree/`。FlowTree 自己仓库根忽略 `.flowtree/` 是本仓库的运行状态，不是被测项目布局。
- **已有忽略规则冲突时只报告，不宣称布局安全：** `.flowtree/.gitignore` 已存在，则列出缺失规则让用户处理，不静默修改；项目根规则整体排除了 `.flowtree/`，则报告"子目录规则可能无法恢复跟踪"。检查用 `git check-ignore`（项目在 git 内时），判据是**文件是否被忽略**，不要求空目录出现在 `git status`。
- 当前验证引擎**不会**读取 `flowtree.yaml`：它读的是 FlowTree 侧的工作区配置。因此 B1 只完成"初始化 + 起草"闭环，用户仍须显式用路径或工作区配置指向故事与映射；`project init` 会打印建议的工作区片段，不写主机配置，**不宣称完整接入已完成**。

## 4. 指纹现状（更正第 2 版的说法）

- 已解决：`service._spec_files` 已排除本次明确读取的故事与映射文件，它们各有独立摘要，入库不会因此重复计入工作区指纹。
- **仍未解决：** 指引（此前已记录）、草稿、`flowtree.yaml`、其他新增配置是否排除。它们若位于被测项目内，**写入或修改它们可能使该项目已有证据"待更新"**（例如在已有证据的项目里运行 `draft`）。

## 5. 文件系统安全（B1-a、B1-c）

- 写入前取真实路径，必须位于项目根内。`.flowtree` 或任一待写目标是符号链接、或路径类型冲突（应为目录却是文件等），**拒绝并报告**，不沿链接写出项目。
- 已存在的普通文件只保留并报告，不覆盖。
- 草稿文件名只取**通过校验的** ID（沿用工作区的 ID 规则：字母数字开头，字母数字、下划线、连字符，最长 64）；含路径分隔符、`..`、空值的 ID 拒绝。文件名不直接来自模型原样输出。

## 6. AI 调用边界（B1-b）

**配置字段（来自第 9 节选定的本机位置，示例）：**

```yaml
ai:
  protocol: openai_chat      # 首版唯一协议：OpenAI 兼容的聊天补全
  base_url: https://api.deepseek.com
  path: /chat/completions
  model: deepseek-chat
  key_env: DEEPSEEK_API_KEY  # 只写环境变量名
  connect_timeout_s: 10
  total_timeout_s: 60
  max_tokens: 4096
  max_input_bytes: 200000
  max_response_bytes: 1048576
  max_calls_per_run: 1
```

示例值仅为示意，实施时按官方支持值核对；核心代码不写死提供方或模型名。

**协议。** 只实现 `openai_chat`，只依赖最基本的结构（消息进、文本出，用量字段可缺）；不依赖流式、工具调用、JSON 模式。接口不兼容时**报告缺哪些字段，不自动改协议重试**；新协议另加适配器。只换地址不等于兼容。

**URL。** 最终地址 = `base_url` 的路径前缀 + 相对 `path`（保留 `/v1` 等前缀，不重复拼接）。`path` 必须是相对路径，不得含主机、`..`；`base_url` 不得含用户名密码、查询串、片段；必须 `https`（本机回环除外）；最终主机必须等于 `base_url` 的主机。**首版禁止任何重定向**（遇到 3xx 报错，不再发送第二次请求）。

**本机配置不天然可信。** 项目里可以被附带未跟踪的 `local.yaml`，或指向别处的符号链接，所以"放在本机文件里"本身不构成同意。因此：
- **每次发送前都要授权，`ai check` 也一样**（它同样发送密钥）。授权前展示：协议、最终完整地址、配置来源文件、将使用的密钥变量名（不显示值）、`draft` 还要显示发送的文件与字节数。
- 交互环境需要用户明确确认；**非交互环境没有明确的按次授权参数就退出，不发任何请求**。授权参数须带最终地址（`--allow-send <完整地址>`），地址不符即拒绝。首版不做持久信任库。
- `--dry-run` 只是预览，**不构成同意**，也不发请求。

**错误与日志。** 不原样输出服务端响应正文（可能回显密钥或需求内容），只记录状态码、错误类别、耗时。密钥只来自环境变量，不进文件、日志、错误信息、命令行参数，界面只显示"已设置/未设置"。
**限制与失败。** 有连接超时与整体超时；输入与响应有大小上限；输出被截断、无文本、非预期结构都有明确错误；超时只说"请求结果未知，服务端可能已处理并计费"，**不声称未收费**；不自动重试；每条命令最多 1 次，另有 `max_calls_per_run` 硬上限。调用记录写入 `runs/ai/`（时间、地址、模型、耗时、用量、输入摘要、状态），默认不保存完整提示词。需求文档按"不可信数据"处理，模型输出只按 YAML 数据安全解析，绝不执行。

## 7. 草稿输出与确认（B1-c）

**响应结构。** 要求模型返回一个 YAML 映射，只含两个键：`story`（候选故事）和 `questions`（假设与待确认项的列表）。`story` 单独交给现有**严格**故事模型校验；`questions` 单独校验为字符串列表。缺少 `questions` 键与明确返回空列表**区别对待**（前者是格式错误；后者仍显示"模型未列出待确认项，需负责人自行核对"，**空列表不等于已确认**）。

**元数据由工具填写，不信任模型自报。** 写入 `drafts/<id>.draft.meta.yaml`：`status: draft`、实际来源文档路径与摘要、实际地址与模型、生成时间、提示版本、`story_digest`（对草稿故事内容计算）、校验结果与待确认项。`drafts/<id>.draft.yaml` 只含故事结构，不夹带元数据（字段是否被严格模型拒收，实施前对照现有模型核实）。

**绑定与失效。** 元数据绑定草稿故事摘要；草稿被手改、摘要不符时，不再把旧校验结果和待确认项显示为当前结果，而是提示"草稿已改动，需重新校验"。

**成组写入。** 两个文件作为一组：先写到临时位置，两者都成功再就位；任一同名文件已存在则整体拒绝；失败不留下会被计为有效草稿的半组文件。

**不转正。** 校验通过只证明格式与引用有效，不代表需求正确；任何输出不写"已确认"。不覆盖现有故事；转正是负责人确认后的手工动作，B1 不实现转正命令。工具持续显示"有 N 份草稿待确认"。

## 8. 三个小批次与离线验收标准

不使用真实模型、不花钱。每批单独复验。

**B1-a 初始化**
1. 空示例项目 `project init`：产出与第 3 节一致；重复执行不覆盖；断网结果相同；项目根 `.gitignore` 与已有文件不变。
2. 用 `git check-ignore` 检查：应入库的文件未被忽略，应忽略的被忽略；已有 `.flowtree/.gitignore` 或根规则冲突时报告而不改动、不宣称安全。
3. `.flowtree` 为符号链接、目标路径类型冲突、真实路径越出项目：拒绝，项目外无任何写入。
4. 旧 `flowtree init / run / status / watch` 沿用现有回归，行为不变；未配置 AI 时 `ws verify / status / story validate` 结果不变。

**B1-b 通用调用（`ai check`）**——用标准库在本机起 OpenAI 兼容形状的假服务，真实走 HTTP：
1. **未授权零请求**：`ai check` 在非交互且无授权参数时不发请求（假服务无记录）；授权地址不符也不发。`--dry-run`/`--offline` 零请求。
2. 地址拼接：保留路径前缀、不重复、`path` 不能改主机；含凭据/查询串/非 https（回环除外）被拒绝。
3. **重定向零后续请求**（假服务返回 3xx，后面没有第二次连接）。
4. 成功；鉴权失败；限额；连接超时与整体超时；响应缺字段；输出截断；无文本；响应过大——均有明确错误，不自动重试，不改协议重试。
5. 假服务在响应里回显假密钥：日志、错误信息、输出均不出现该密钥。
6. 用已知假密钥全文搜索配置、日志、输出、命令行参数，均不出现。

**B1-c 草稿**——沿用假服务：
1. 同样的未授权零请求、授权地址绑定、`--dry-run` 零请求。
2. 返回非法 YAML、缺 `story`、缺 `questions`、`questions` 为空、故事校验不通过：各有明确结果；缺键与空列表区别对待。
3. 越界或非法 ID（含 `../`、分隔符、空）被拒绝，项目外无写入。
4. 成组写入：同名任一文件存在则整体拒绝；中途失败不留半组；元数据 `status` 恒为 draft，来源与模型由工具填写（模型自报的值被忽略）。
5. 手改草稿后，摘要失配，旧校验结果不再作为当前结果显示。
6. `draft` 前后现有故事文件字节不变。

**真实调用（手工，一次）：** 负责人用自己的 DeepSeek 密钥运行 `ai check` 与一次 `draft`，亲眼看草稿与待确认项。不计入自动验证。

## 10. 从初始化到执行验证：现状与接通方案

**今天就能跑的命令（不需要工作区配置，路径显式传入）：**

```bash
flowtree story validate <故事目录> --mappings <映射目录>
flowtree story plan     <故事目录> --mappings <映射目录>
flowtree verify         <故事目录> --mappings <映射目录> --project-root <项目> [--python <解释器>]
flowtree story status   <故事目录> --mappings <映射目录> --project-root <项目> [--python <解释器>]
```

**默认方案下的完整命令示例，以及每步现状：**

| # | 命令 | 现状 |
|---|---|---|
| 1 | `flowtree project init .` | B1-a，待做 |
| 2 | `flowtree ai check --allow-send <地址>` | B1-b，待做；会收费 |
| 3 | `flowtree draft docs/需求.md --allow-send <地址>` | B1-c，待做；会收费 |
| 4 | 负责人确认草稿，手工移入 `.flowtree/stories/` | 人工动作，设计如此 |
| 5 | 编写映射与测试放入 `.flowtree/mappings/` | **手工**；映射起草与测试生成属后续批次 |
| 6 | `flowtree story validate .flowtree/stories --mappings .flowtree/mappings` | **今天可跑**，但要手敲两个路径 |
| 7 | `flowtree verify .flowtree/stories --mappings .flowtree/mappings --project-root . --python <py>` | **今天可跑**，路径、解释器每次手敲 |
| 8 | 浏览器看结果页 | **需要手工**：页面只读 FlowTree 侧 `workspaces.yaml`，要手写一段工作区配置 |

**缺口：** `project init` 写出的 `flowtree.yaml` 目前没人读。用户每次要手敲路径，页面还要手拼工作区配置。这与"少操心"的目标有差距，不能把"文件建好了"当成"项目接入完成"。

**最小接通方案（建议作为 B1-d，排在 B1-a 之后、两个 AI 批次之前）：**

1. 新增一个加载函数：读项目的 `flowtree.yaml`（可移植：故事/映射/指引的相对路径、测试环境变量等非敏感项）与 `local.yaml`（本机：解释器路径等），**产出与现有工作区相同的 `Workspace` 对象**。判定仍由同一核心服务做出，不另写一套。
2. 现有 `ws status / verify / guides / context` 增加 `--project <目录>`，代替工作区 ID：步骤 6、7 缩短为 `flowtree ws verify --project .`。
3. 新增独立命令 `flowtree project register [目录]`：在 FlowTree 侧的工作区配置里新增一条指向该项目的条目（只写项目路径，显示将写入的内容，已存在不覆盖）。注册后页面即可看到，不再手写配置。该命令不执行测试、不联网。
4. 安全：项目里的配置只能写相对路径与非敏感环境变量，**不得含 AI 地址、密钥、绝对路径的解释器**；越出项目根的路径拒绝。执行测试本来就运行项目自己的代码，这一信任前提沿用，不因此放宽。

**消除后的完整路径：** `project init` → 写故事与映射 → `ws verify --project .` → `project register` → 打开页面；其中只有"写故事与映射"在映射起草批次之前仍需手工。

**推荐批次顺序：** B1-a 初始化 → B1-d 接通 → B1-b 通用调用 → B1-c 草稿。理由：B1-d 只用已有代码，风险小，能让 B1-a 的产物立刻可用；两个 AI 批次涉及网络与计费，放在后面。离线验收标准在 B1-d 增加：`--project` 与等价的工作区配置得到相同状态；越界路径、密钥字段被拒绝；`register` 不覆盖已有条目；未使用 `--project` 的现有命令行为不变。

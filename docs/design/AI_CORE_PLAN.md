# AI 核心总体规划：接入、状态与评测

日期：2026-11-14（第 2 版）。作者：Claude。状态：**规划提案，不是实施授权；不写代码、不调用收费 API**。
来源：负责人判断——已完成的故事契约、证据、页面、人工验收"谁都能做"，不是 AI 工程核心；评测、AI 接入、状态管理是核心。具体设计是 Claude 的建议，并已按 Codex 的[规划复核](../reviews/AI_CORE_PLAN_REVIEW.md)修订。
与 [`B1_PROJECT_INIT_AI_PROPOSAL.md`](B1_PROJECT_INIT_AI_PROPOSAL.md) 的关系：该提案的第 3 版安全设计、离线验收标准仍然有效，其 B1-a/b/c 并入下面的 P1-1、P1-2；其第 10 节的 `--project` 接通与 `register` 留作后续。

第 2 版相对第 1 版的主要修正：不再承诺"确认一定来自真人"；状态改为由几类事实计算，不用互斥直线；评测先冻结标注表并拆分参照标签；不再称"留出样本"；P0 缩小；P1 拆为三个小批次并给出完整命令链；补充外发范围、预算登记、提示注入等边界。

## 1. 现状判断

| 部分 | 性质 |
|---|---|
| 故事格式、映射、真实执行 pytest、证据与指纹、结果页、人工指引 | 通用工程。此后暂停**无关扩展**，仍允许起草闭环必需的最小接入改动 |
| 模型调用、AI 产出的管理、AI 质量的度量 | 目前为零：故事、测试、修复都是人与 AI 在会话中协作完成，工具里没有调用模型的代码 |

已有部分的价值是 AI 产出的**确定性判定来源**，但它能证明的只有格式、引用、测试执行和证据有效性，**不能证明 AI 理解了真实需求**。也不为"AI 工程"的标签牺牲"少配置、能使用"的产品目标。

## 2. 职责划分（不是四套基础设施）

A 调用边界、S 状态、G 生成、E 评测是**职责划分**。首版各自只做最小切面，不建通用工作流引擎，也不建评测平台。

| 职责 | 首版最小切面 |
|---|---|
| A 调用边界 | 一种通用协议、发送授权、密钥与端点安全、超时与大小上限、预算登记 |
| S 状态 | 草稿的内容摘要、校验结果、确认记录、取代关系——几类事实，按需计算展示 |
| G 生成 | 单文档故事起草（测试生成与修复闭环保留方向，不提前展开） |
| E 评测 | 冻结的标注表 + 离线重放保存的模型输出 + 计数报告 |

## 3. 状态与确认

### 3.1 能承诺与不能承诺的

- **不能证明确认来自真人。** 本地 CLI 与文件模型下，AI 也能调用同一命令、写同一文件或冒填姓名。角色字符串不是身份认证，首版也不引入身份系统。
- **能承诺的：** 生成流程里没有任何自动确认路径；确认是独立的显式动作；确认记录绑定对象摘要并带声明的确认者。测试只证明**程序路径的边界**，不证明真人操作。
- 校验通过与确认都**不代表逻辑验收或人工验收通过**。

### 3.2 用几类事实计算状态，而不是一条直线

| 事实 | 内容 |
|---|---|
| 内容摘要 | 草稿故事内容的摘要 |
| 校验结果 | **针对某个摘要**：有效 / 无效（含原因）/ 校验出错（工具故障）。内容变了，旧结果不再作为当前结果显示 |
| 确认记录 | 人的声明：确认的对象与摘要、**依据的需求源文件及其摘要**、声明的确认者、时间、依据说明；可被**撤回**或**更正**（追加记录，指向被更正的那条） |
| 取代关系 | 新版本指向被取代的旧版本 |

展示状态由这些事实按需推出：例如"内容已变，校验与确认均不适用于当前版本""已确认，但需求原文自确认后已变化"。校验失败、校验出错、内容变化、确认撤回都能表达，不会都落回一个含糊的"草稿"。

### 3.3 确认的边界

- 确认记录绑定明确对象与摘要，并要求确认时该摘要的校验有效（否则拒绝记录，原因说明）。
- **"移入 `stories/`"不等于确认。** 首版也不新增"自动转正"。本批只限定：**新生成的产出不会自动进入正式路径**。
- 不在全局禁止现有的 draft 状态故事参与验证——那会改变现有引擎契约。既有"规则"维度的显示照旧如实。
- 需求原文更新后，不能只因 YAML 没变就声称仍对应最新需求，所以确认记录里要有需求源摘要。

### 3.4 与轮次、发现的衔接

确认事件**只描述"确认哪份内容"**，复用已有概念（对象、摘要、操作者声明、时间、依据、更正关联）；不顺便实现人工验收、发现处置、发布批准。**AI 调用、执行 run、人工验收轮次分别命名，不复用一个生命周期。** 将来这些记录引用现有的，不再复制一套可分别修改的结论。

### 3.5 调用与预算

- **请求前**先持久登记"开始/占用额度"，并处理并发与崩溃；不能只累计完成记录，否则超时或两个进程同时调用可以绕过上限。
- 无法准确估价时，只承诺**调用数与令牌/字节上限**，不声称货币预算的硬保证；用量未知就保留"未知"。
- 超时的调用记为"结果未知"，不说未计费。

## 4. 评测：先冻结标注表，再计数

### 4.1 参照物的真实情况

US-23/US-24 **不是完整的已确认标准答案**。`RULE_CONFIRMATION_US23_US24.md` 明确：只有部分核心规则得到确认，重进、重复提交的具体行为、审批权限等仍有待决项；人工验收通过也不补齐需求确认。所以不能把整份 YAML 当逐条标准答案。

### 4.2 标注表（评测前先冻结）

表的行：**原文片段 → 原子规则 → 来源位置 → 确认状态**。确认状态分四类：

| 标签 | 含义 | 是否进"已确认规则"的分母 |
|---|---|---|
| 原文明确 | 需求原文明确要求 | 是（且需有确认依据） |
| 推断 | 从原文合理推出，原文未明说 | 否 |
| 夹具 | 为测试环境所需的设定 | 否 |
| 待决 | 尚未定的事项 | 否 |

每个标签与每次修订保留依据。首版**完全手工标注**；脚本只做统计与追溯，不要求算法自动判断中文需求语义。

### 4.3 计数而不是打分

分别报告（给出分子、分母和实际案例），**不合成单一质量分数**：
- 格式一次通过情况；
- 对"原文明确且已确认"规则的**覆盖与遗漏**；
- 与原文**矛盾**的断言；
- **无依据断言**：把无来源的假设写成确定规则；
- **合理建议**：明确列入待确认项的，与上一项**分开计数**——"多余"不等于"编造"；
- **来源位置语义核对**：来源路径或行号存在不等于内容支持该规则，要人工逐条核对；
- **歧义发现**：模型提出的待确认项里有多少对应人工标注的真实歧义（分母由人工标注给出）；不奖励"堆满问题"。

F-04 可作为"提示文字交互"问题的案例，但原始输入若没有"必填、可见提示"的要求，**不得因为模型没生成后来才确认的规则而惩罚它**；可以单独评估它是否发现了歧义并提问。

### 4.4 诚实边界

- 两条故事已被我们反复查看和调试，**不能称为"独立留出样本"**，最多叫"本次后续不用于调试的验证样本"。真正的留出样本要另选，并在调试**之前**冻结；首版不为凑统计结论而扩大范围。
- 样本只有两条，结果是演示方法与暴露问题，不是统计结论；报告写明样本量。
- 外部模型输出不保证逐字可复现，也不把温度设为 0 当成确定性保证。**可复核的是比较报告：** 固定输入、提示版本、参数、标注表；保存输入与输出摘要、模型声明、时间；重复运行则报告各次结果。
- 评测的是"起草故事的质量"，**不要把"会写漂亮 YAML"当作能正确生成测试或修复代码**。
- 参照故事最初由 Claude 起草再由负责人确认，所以结论只能是"与已确认部分的一致程度"，不是"与真实需求一致"。
- 不用另一个模型作为唯一裁判。

## 5. 外发与输入边界

- **外发范围：** 只读命令明确指定的需求文件，发送前显示最终发送的内容范围；**不自动递归收集仓库、环境变量或源文档中的链接**。
- **长文档：** 按字节/输入预算**拒绝并说明**，不静默截断；检索与分块以后再做。
- **提示注入：** 需求文档与模型输出都是数据；不因其内容执行命令、读取密钥、改目标端点或确认任何内容。畸形输出、无文本、被截断均有明确失败路径，不自动重试。
- **产出与保密：** 草稿与模型响应可能含需求原文和敏感内容；"可入库"不等于"全部适合入库"，保存时原始响应脱敏；沿用 B1 的成组写入、不覆盖、路径约束。
- **变异评测（P2）：** 固定适用范围，排除无效与等价变异，区分"断言抓住业务错误"与"测试无法编译、环境失败"，不以写几个容易抓的变异就声称测试全面。

## 6. 阶段

| 阶段 | 内容 | 说明 |
|---|---|---|
| **P0 整理** | 只索引**本次相关的现行规范**与明确被替代的提案（含给缺提示的旧规划补"已被替代"一行）；不要求索引全部历史文档，也不阻塞开发 | 小提交 |
| **P1-1 最小接入与调用** | 初始化项目入口（`project init`）、通用协议/DeepSeek、用户级配置、发送授权、预算登记、假服务离线测试 | 用户能实际运行 |
| **P1-2 单文档起草** | `draft`：严格草稿、来源与内容摘要由工具填写、独立校验、状态展示；既有引擎仍可独立运行 | 并入 B1-c |
| **P1-3 确认边界与小型评测** | 显式确认记录的最小切面；冻结标注表；离线重放保存的输出，出计数报告；**真实调用按已批准的预算另做** | |
| P2 / P3 | 测试生成与变异评测；修复闭环（函数调用、agent 循环、隔离应用、权限边界） | 只保留方向，不提前展开 |
| P4 | `--project` 接通、`register` 等便利 | 沿用 B1 提案第 10 节 |

小批次是**实施拆分建议**，不等于已获得实施授权。每批仍交付：步骤卡、验收清单（从空目录开始，分"自动证明"与"你亲眼确认"两栏）、取舍记录，独立提交。

## 7. 从项目入口到草稿、校验、评测报告的命令链

| # | 命令 | 作用 | 现状 |
|---|---|---|---|
| 1 | `flowtree project init .` | 建立项目内 `.flowtree/` 布局 | 待实现（P1-1） |
| 2 | `flowtree ai check --allow-send <地址>` | 检查配置并发 1 次最小请求 | 待实现（P1-1）；收费 |
| 3 | `flowtree draft <需求文件> --allow-send <地址>` | 起草故事草稿与元数据 | 待实现（P1-2）；收费 |
| 4 | `flowtree draft check <id>` | 重新校验草稿并显示当前状态（内容变了则提示旧结果不再适用） | 待实现（P1-2）；核心复用现有 `story validate` 的校验逻辑 |
| 5 | `flowtree story validate <草稿文件>` | 直接用现有校验器检查故事文件 | **已存在** |
| 6 | `flowtree draft confirm <id> --by <名字> --basis <依据>` | 追加确认记录（绑定摘要与需求源摘要；摘要校验无效则拒绝） | 待实现（P1-3） |
| 7 | `flowtree eval draft --annotations <标注表> --response <已保存输出>` | **离线**重放保存的输出，按冻结标注表计数，输出报告 | 待实现（P1-3）；不调用模型 |
| 8 | 手工把确认后的故事放入 `stories/`，写映射与测试 | 进入已有的验证流程 | 手工；转正命令不在本规划内 |
| 9 | `flowtree verify …` / `flowtree ws verify <id>` | 执行逻辑验收 | **已存在**；`--project` 接通属 P4 |

## 8. 风险

| 风险 | 缓解 |
|---|---|
| 评测过拟合两条故事 | 标注表先冻结；报告写明样本量；调试用样本与"后续验证样本"分开 |

| 产出被当成事实 | 无自动确认路径；确认绑定摘要与需求源摘要；校验无效则拒绝确认；测试覆盖程序路径边界 |
| 范围蔓延 | 严格按批次退出标准；P1 之外只保留方向 |

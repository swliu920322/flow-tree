## 1. 用户要解决的问题

用户希望提供用户故事，让 FlowTree 读取故事、项目文档和代码，梳理实际使用流程，发现规则与测试缺口，生成或补充测试，实际执行验收，展示进度，并在明确验收依据下协助修复代码。

工具供不同项目使用。大模型由用户自己的 API 付费与调用；FlowTree 提供规范、提示词、规则、执行编排、证据与可视化，不做模型供应商，也不替用户经营业务数据库。

用户对当前项目有过明确顾虑：测试全绿不等于场景完整，不愿先在有大量已知潜在问题的版本上反复手测。因此 FlowTree 的目标应是缩小未知范围、把未覆盖/未执行明确暴露出来，再组织聚焦的人工验收，不能承诺数学意义的全场景穷尽。

## 2. 已明确的产品偏好与边界

这些来自用户先前讨论，应延续，除非用户主动变更：

- 从用户在客户端的真实使用旅程出发，再关联接口、后端状态和业务不变量；不让用户先维护一棵技术 ID 树。
- 默认以纵向、从上到下的正常主流程展示。异常、输入边界与恢复分支在节点旁用 `+` 展开。
- 折叠只改变显示；未执行、失败、待决策的分支仍须在主节点显示数量，不能被藏起来。
- 边界拒绝通常结束本次操作；驳回重提、网络恢复等可返回/汇合主线。不能把“分支”一律实现为没有后续的死路。
- 稳定 ID 用于引用与追溯，默认 UI 弱化 ID。用户流程可有重试环，开发任务依赖 DAG 则须无环，两者分开建模。
- 保留测试生成、逻辑检查、最小代码修复、进度和可视化。修复服务于明确验收条件，避免无依据的重构、功能扩展和过度设计。
- 第一阶段聚焦已有项目的编码层。业务表设计、ORM、业务迁移和真实数据管理由项目负责，通过环境/夹具/测试适配器调用。
- FlowTree 自己可保存故事、运行和证据；这与通用业务数据库平台是两回事。
- CLI、MCP、Web 应共用领域模型和结果语义。三个入口不应各维护一份规则与状态。
- 用户希望用文档持续沉淀，不希望换会话后失忆、反复问同一已确认问题或无限扩展同类复验。

## 3. 最新 harness 讨论：判断与建议，不要误记为全部已经实施

用户提出：仅靠 prompt 似乎也能做，工程化与可视化的价值何在？这是否属于通用业务 harness，需要转方向吗？

Codex 的建议是：**保留产品方向，在内部采用 harness 的组织方式；先做“面向已有软件项目、故事与验收契约驱动的工程工具”，不先扩大成任何业务都能编排的通用 Agent 平台。** 用户随后要求把记忆写成交接，并转到 FlowTree 会话继续安排；尚未逐项批准下面所有模块的实现方案。

这里 harness 指围绕模型的执行框架：上下文准备、工具调用、持久状态、验证、恢复、停止条件和运行记录。它本身就是工程代码，与传统开发不矛盾；不取决于是否使用某个带 harness 名称的框架。

职责建议：

| 内容 | 模型可做 | FlowTree 的确定性职责 |
|---|---|---|
| 需求理解 | 提取故事、识别歧义、提出规则草稿 | 保留来源、版本及确认记录 |
| 场景覆盖 | 提议边界与异常、映射现有测试 | 展示已定义范围、未覆盖项及不适用项，不虚构穷尽 |
| 测试生成 | 生成有业务断言的测试草稿 | 校验产物、执行真实命令、解析结果 |
| 代码改进 | 分析原因、提出小补丁 | 关联规则/缺陷、控制范围、安排回归 |
| 进度 | 提供分析意见和下一步建议 | 根据证据计算状态，不能直接相信模型说“通过” |
| 长任务 | 选择建议动作、生成交接摘要 | 记录任务与历史，限定重试/预算/恢复和停止策略 |
| 人工验收 | 整理待验步骤 | 只接受真实人工操作的签字，不由模型代填 |

Prompt 是策略的一部分，应版本化；它不是唯一事实来源。故事/规则契约、执行记录和原始证据才是状态依据。固定状态转换、Schema 校验和结果解释适合代码实现；按项目名硬编码业务答案不适合作为通用能力。

- https://www.anthropic.com/engineering/harness-design-long-running-apps

## 4. BYOK 与两种执行方式

用户希望配置通用大模型调用。建议分开两种适配器：

1. 模型调用适配器：provider/协议、base URL、model、密钥环境变量或安全存储引用、结构化输出与工具调用能力、超时/费用上限等。不要假设所有供应商兼容接口的能力完全一样。密钥不能提交到故事文档、`.flowtree` 状态文件或 Web 前端配置。
2. 任务执行适配器：文件读取/搜索、项目测试命令、受控补丁、工具结果与错误。接上模型 API 不会自动获得完整编码 Agent 的行为，需要工具和有边界的执行循环。

可以共存的模式：
- FlowTree 自主编排：Web/CLI 使用用户 API 完成分析与生成，并调用执行层。
- 外部 Agent 编排：Codex/Claude 等通过 CLI/MCP 调用 FlowTree；模型与凭据由外部宿主拥有。这种模式不应强迫用户额外配置一遍 FlowTree 的模型。

两种方式共用故事、运行与证据契约。第一版先选一个最小工作路径；可以先复用外部编码 Agent，或采用受控补丁生成，不必先自建完整通用自主编码平台。模型能提议动作，但不能自行赋予权限、伪造通过或改写人工确认。

这是一份待在新会话细化的建议，不是要求同时实现所有入口和通用框架：

1. 选三条真实故事验证格式：零关系 A 任务完成、家庭任务驳回后重提、克制记录响应丢失后确认原请求。
2. 写出 Schema/引用校验和故事到测试的显式映射，保留来源与未知规则。
3. 接入样本项目已有 pytest/Flutter 的真实结果，不从零重写其完整测试库；测试生成产物只能标“已生成/待执行”。
4. 建立 run/attempt/event/evidence 的最小记录，包括真实命令、退出码、断言失败与环境搭建错误、计数、原始报告及基线。
5. 消除产品路径上的固定成功、预填人工签字与错误进度。演示数据明确标 demo，不混入真实验收。
6. 做纵向正常流程与 + 分支，并在折叠节点暴露失败/未知数量。
7. 在此基础上接模型分析、缺陷修复与有限次数的回归；最后统一 CLI/MCP/Web 对同一领域服务的调用。

修复循环要有成本/轮次限制、重复失败识别、无进展停止、已确认问题关闭和新问题分离，避免 SESSION 审计那样无限延长同一轮。模型可以建议继续，停止条件由执行层和产品范围决定。

最小成功标准示例：一条故事关联真实测试入口；运行时确实启动测试；失败能追溯到场景；补丁后回归通过；切换新会话仍能从证据继续；UI 不把未执行分支或人工待验显示成通过。

## 11. 从这次审计应沉淀的产品能力

- 200 或测试全绿不代表业务正确，更不代表客户端入口存在；断言要检查状态、余额、权限和副作用。
- 幂等和并发不能只用单进程/SQLite 代替真实数据库多进程；环境未验就诚实标未验。
- 会话正确性不能只比较 token 字符串：同账号同秒可能返回相同 JWT，操作归属需要独立身份/轮次。这是样本测试知识，不是每项目都要照搬字段。
- 人工确认的规则、已证实缺陷、测试搭建错误、技术债、明确范围外必须区分。
- 默认 known skip/xfail 是登记缺陷，不是完成；修好后要去除，避免永久掩盖。
- 测试补充必须登记到显式模块清单；路径映射不等于实际被该范围执行。
- 证据需关联源码和工作区，不能拼不同批次结果做虚假的 clean-HEAD 全量证明。
- 隔离执行要有资源所有权与清理核对，避免旧脚本默认碰开发/生产数据。FlowTree 不因“自动验收”就获得真实库操作权。
- 验证对象与验证器本身均可能出错；先确认真实失败原因，再登记产品缺陷。
- 能关闭已修复问题同样重要，不能每换上下文又回到旧问题和已确认决策。

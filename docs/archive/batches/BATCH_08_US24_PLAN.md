## 2. 流程拆解（提交 → 待审 → 驳回 → 修改重提 → 批准）

主流程与分支（现有 `TASK-B-001` 故事已覆盖这条路径，不需要改故事文本；是否要补"待审期间有效进度/奖励不变"的显式断言，见第 4 节）：

1. 执行人看到本人 B 任务与凭证入口（STEP-01）。
2. 执行人提交凭证 v1 → 任务 `submitted`（STEP-02）。此时：有效进度 0、B 余额 0、无 B 账本记录。
3. 发行人驳回并写原因 → 任务 `rejected`，v1 `rejected` 并保留原因（CASE-01）。此时进度仍 0、余额仍 0。
4. 执行人看到原因，修改后重提 v2 → `submitted`（CASE-01 回到 STEP-03）。进度仍 0、余额仍 0。
5. 发行人批准 → `done`，v2 `approved`（STEP-03）。此时才：进度 1、该发行人账下 B 余额 +25、账本恰 1 条（STEP-04）。
6. 边界：陌生人批准/驳回 403（CASE-03）；对已处理的再批准/再驳回/再提交 409，不重复发奖。

### 4.1 界面 vs API 的分工

| 步骤 | 执行方式 | 原因 |
|---|---|---|
| 注册 爸爸、孩子（另可注册 妈妈 作对照发行人） | API 准备 | 非本故事关注点，已被 B-001/A 联调覆盖 |
| 建立发行人→执行人关系（邀请/接受） | API 准备 | 同上 |
| 爸爸建 B 任务并派发给孩子（奖励 25、目标 1） | API 准备 | 夹具 |
| 孩子登录、看到任务、**提交凭证 v1 与重提 v2** | **界面**（真实 TasksPage，输入凭证） | 故事主体：执行人侧 |
| 孩子界面查看驳回原因 | **界面** | CASE-01 |
| **发行人驳回、批准** | **API（以爸爸 token 调真实后端）** | 第二个账号的界面登录会让客户端单会话/全局状态复杂化；审批动作走真实后端路由，不是模拟 |
| 每阶段的有效进度、B 余额、账本、提交历史 | 界面读取 + API 独立读取，两者对照 | 防止"界面与后端不一致" |
| 访问日志计数（待审/驳回期间没有任何奖励相关的写请求以外的异常） | 后端 access log | 沿用现有联调手法 |

说明：这样"发行人审批"是**真实后端、真实第二账号、API 驱动**，而不是"发行人界面"。发行人侧界面（审批弹窗）仍只有模拟/客户端层级证据，我会在页面上如实写明，不声称覆盖。若 Codex 要求发行人界面也走真实，需要第二个会话切换，那是另一批的范围。

### 4.2 断言（每阶段）

| 阶段 | 断言 |
|---|---|
| 初始 | 进度 0/1、孩子在爸爸账下 B 余额 0、B 账本空 |
| v1 提交后（待审） | 任务 submitted；进度仍 0；B 余额 0；账本空；提交历史 1 条 v1 submitted |
| 驳回后 | 任务 rejected；原因文字可经界面与 API 读到；进度仍 0；余额 0；账本空；v1 rejected 保留原因与审批人 |
| 重提后（待审） | 任务 submitted；进度仍 0；余额 0；账本空；历史 2 条：v1 rejected 原凭证与原因保留，v2 submitted |
| 批准后 | 任务 done；进度 1/1；爸爸账下 B 余额 +25；账本**恰 1 条**（delta 25、before 0、after 25、归属爸爸）；妈妈账下 0（对照）；v2 approved |
| 不重复发放 | 对已批准再批准 → 409；再驳回 → 409；再提交 → 409；账本仍 1 条，余额仍 25 |
| 越权 | 陌生人（或妈妈）批准/驳回 → 403，状态与账本不变 |
| 一致性 | 界面显示与 API 一致；对账接口（B 侧如有）平衡，若没有 B 对账接口则不声称 |

待实现时需先核对的事实（现在未验证，列为实现前检查，不假设）：B 余额与账本通过哪个接口读（`/auth/me` 的 `balances_b` 已见于后端测试；B 账本是否出现在 `/ledger/my`）；`/tasks/my` 里"有效进度"字段名；若目标 1 时批准即 done，进度观察点只有 0→1。是否另用目标 2 观察 0→1/2 更直观，请 Codex 定；默认只做目标 1，沿用现有 B-001 前置条件。

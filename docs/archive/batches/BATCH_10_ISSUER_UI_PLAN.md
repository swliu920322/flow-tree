## 2. 最小真实界面联调方案

复用：`RealBackend`（隔离临时 SQLite、随机端口、信号清理）、`kit.dart` 的 `BackendApi`、伴随运行时 `backend-python`。不碰真实库，不联网，不用付费 API。

### 2.1 推荐：一个"双界面"测试（新文件，不动已验收的 `real_backend_b_review_test.dart`）

同一个客户端实例顺序切换账号（单进程、单后端；**不是**两个设备同时在线）：

| 步 | 账号 | 方式 | 内容与断言 |
|---|---|---|---|
| 0 | — | API 准备 | 注册爸爸、妈妈、大宝、外人；建立两条发行人关系；妈妈预置 B=5；爸爸建 B 任务（奖励 25、目标 1，**夹具**） |
| 1 | 大宝 | 界面 | 登录 → 提交 v1 → 待审（沿用现有断言：按 assignmentId 定位卡片、`0/1 次`、审批中；客户端余额按发行人 id 归属） |
| 2 | 大宝→爸爸 | 界面 | 账户弹层退出登录 → 登录页登录爸爸 |
| 3 | 爸爸 | 界面 | 切到管理视角：审批中心 (1)，显示"申请人：大宝"与 v1 凭证文字；**点驳回，输入原因，确定**。断言：审批中心清空/(0)；API 读到任务 rejected、原因与输入一致、v1 rejected 且审批人为爸爸；大宝账下 B 与流水不变（批准前不增加） |
| 4 | 爸爸→大宝 | 界面 | 退出、登录大宝：任务卡显示驳回原因、`0/1 次`；修改后**重新提交 v2**；断言同前（待审，余额不变，历史 2 条：v1 rejected 保留原凭证与原因、v2 submitted） |
| 5 | 大宝→爸爸 | 界面 | 登录爸爸：审批中心 (1)，显示 v2 凭证；**点批准**。断言：审批中心清空；API 读到 done、进度 1、v2 approved、爸爸账下 +25、妈妈账下仍 5、新增恰 1 条流水（delta 25, before 0, after 25，归属爸爸） |
| 6 | 爸爸→大宝 | 界面 | 登录大宝：卡片 `1/1 次`、已完成；账户弹层爸爸 25、妈妈 5；提交历史 v1 已驳回（含原因）、v2 已通过 |
| 7 | — | API/日志 | 访问日志按实例统计：批准/驳回/提交的状态序列与动作人（驳回、批准各 200 且由爸爸 token 发出）；再批准/再驳回/再提交保留为 API 层 409 检查（界面已无入口，不通过界面造重复） |

保留在 API 层、不改为界面的：外人/妈妈越权 403（界面没有这类入口，且已在 `M-B-REAL-REVIEW` 里覆盖）、重复处理 409、空原因 422。

### 2.2 备选（更轻，若 2.1 运行时间或稳定性不可接受）

只覆盖发行人界面：大宝提交 v1/v2 走 API（已在上一批用界面证明过），爸爸只登录一次：界面驳回 → API 重提 → 界面批准。优点：只有 2 次账号切换；缺点：就不是"两侧都走界面的完整故事"，只能声称"发行人界面的驳回与批准在真实后端上可用"。我倾向 2.1，但若 Codex 觉得切换次数太多，可降级到 2.2。

### 2.3 稳定性设计（沿用已验证手法）

有期限的 `untilFound`/`untilTrue`/bounded `settle`；`HttpOverrides.global = null`、`tester.runAsync`；`SavedGlobals` 恢复；账号切换封装成 `switchTo(username)` 辅助函数（打开账户弹层 → 退出 → 等登录页 → 登录 → 等任务页），失败时给出所在步骤。发行人审批列表在切到管理视角后需等待网络加载，用"审批中心 (N)"文案作等待条件。

## 6. Codex 决定与表述修正（2026-11-11）

1. 采用双界面方案 2.1；只通过界面退出/登录切换账号，不手工换 token、不直接改当前用户；每次切换后核对当前用户 ID。
2. 只走内联审批列表；批准/驳回按钮按"目标任务及当前凭证所在卡片"定位，不按审批中心数量或全局按钮。
3. 新增映射条目、保留旧条目；新条目不覆盖越权分支，CASE-03 继续由已有后端及 API 联调条目验证。
4. 空原因先探测、如实记录，不自动升级为产品规则，不为此扩大范围。
- 表述修正（本文第 2.1 步骤 7 与第 3 节）：访问日志的状态码**不能证明操作人身份**，只用来核对请求结果；操作人由真实登录会话（`AuthService.currentUser`）与提交历史里的 `reviewer_id` 核对；日志不记录 token。新增的映射条目尚未执行时页面应显示"未执行"而不是"未映射"；只有新增测试文件引起的源码指纹变化，才会让旧证据变为过期。

## 7. 实现记录（2026-11-11）

新增文件（仅此一个，LPB 业务源码、既有测试、`kit.dart` 均未改）：`test_integration/real_backend_b_review_two_ui_test.dart`。

**完整测试名（映射用）**：
`US-24 双界面: 大宝提交→爸爸界面驳回(填原因)→大宝重提→爸爸界面批准→大宝核对; 批准前余额与奖励流水不增加, 批准后只记入爸爸账本一次`

**结果**：单跑通过（约 16 秒，隔离临时 SQLite）。过程中有一处我自己的测试问题：账户弹层有滑入动画，动画未停稳就点"退出登录"会点到屏幕外，造成"退出后无当前用户"超时；改为先等弹层停稳再点，并在需要时滚动到可见。

**各阶段（同一个客户端实例，只通过界面切换账号）与断言**：
| 阶段 | 操作方式 | 断言 |
|---|---|---|
| 0 准备 | API | 账号、两条发行人关系、妈妈账下预置 B=5（真实提交+批准）、爸爸建 B 任务（奖励 25、目标 1，夹具） |
| 1 大宝 | 界面登录、提交 v1 | 登录后当前用户 ID=大宝；爸爸这张卡（按 assignmentId 定位）`0/1 次`、审批中；看不到审批中心；待审阶段：爸爸账下 B 不增加、无爸爸奖励流水、B 流水总数不变、妈妈账下仍 5、进度不增加；客户端余额按发行人 id 同样成立 |
| 2 爸爸 | 界面退出大宝→登录爸爸 | 当前用户 ID=爸爸、顶栏显示爸爸；待办视角无审批中心；切到"模板与指派 (管理)"后出现含**当前凭证 v1** 的审批卡片，卡片内是目标任务标题、"申请人：大宝"、驳回与批准按钮各 1；此时没有 v2；**空白原因探测**（见下）；然后在该卡片内点驳回、输入原因、确定；该卡片消失 |
| 2 后验证 | API | 任务 rejected、原因与界面输入一致；批准前各项（余额、流水、进度）不增加；提交历史 v1 rejected 保留原凭证与原因，**reviewer_id=爸爸** |
| 3 大宝 | 界面退出爸爸→登录大宝 | 当前用户 ID=大宝；卡片显示"驳回原因: …"与 `0/1 次`；客户端爸爸账下不增加；点"重新提交"填 v2；待审；历史 [v1 rejected, v2 submitted]，v1 原凭证与原因保留；重提复用同一实例；批准前各项不增加 |
| 4 爸爸 | 界面切换 | 当前用户 ID=爸爸；审批卡片只含**当前凭证 v2**（没有旧 v1）；在该卡片内点批准；卡片消失 |
| 4 后验证 | API | 任务 done、进度 1；余额 {爸爸 25, 妈妈 5}；新增恰 1 条流水（delta 25, before 0, after 25, 归属爸爸），妈妈流水不变；历史 [v1 rejected, v2 approved]，v1 与 v2 的 **reviewer_id 都是爸爸** |
| 5 大宝 | 界面切换 | 当前用户 ID=大宝；爸爸这张卡 `1/1 次`、已完成、无提交入口；客户端余额 {爸爸 25, 妈妈 5}；提交历史显示 第1次打卡已驳回（含原因）、第2次打卡已通过及两次凭证文字；账户弹层显示"爸爸: 25""妈妈: 5" |
| 6 | API/日志 | 再批准、再驳回、再提交均 409，余额与流水不变；日志按该实例：批准 `[200, 409]`；驳回恰 1 次 200、最后一次 409、其余只可能是 422；提交 `[200, 200, 409]`（日志只核对请求结果，不证明操作人） |

**空白原因的界面表现（仅观察，不是产品规则）**：输入三个空格后点"确定"：对话框关闭，**没有任何驳回请求发往后端**（请求状态序列为空），任务仍待审、余额与流水不变。注意探测的是空白字符而不是真正的空字符串；是否应拦截并提示用户，是产品问题，本批未下结论、未扩大范围。测试只断言安全不变量（任务仍待审、无奖励），并把观察结果打印出来。

**变异验证（临时副本 `scratchpad/lpb_copy`，不改原仓库；每次变异后还原并 diff 确认 `lib/` 与原仓库一致；先确认未变异副本通过）**：
| 变异 | 结果 |
|---|---|
| 驳回原因被固定文本替换（含空白探测路径） | 失败，但命中的是空白探测的"任务仍待审"安全不变量，不是我想验证的断言，所以另做下一项 |
| 驳回原因仅在非空时被替换为固定文本 | 失败，命中 `rejection_reason` 与界面输入一致的断言 |
| 点"批准"实际调用驳回 | 失败，命中任务状态应为 done 的断言 |
| 退出登录后不清当前用户 | 失败，命中"退出后无当前用户"（账号切换确实走真实退出，且验证被执行） |
| 主界面任务页的 key 不再随用户名变化（想模拟串号） | **未失败，是等价变异**：退出登录时整个主界面被登录页替换，任务页本就会重建，所以这个变异不改变行为。不把它当作"串号被抓住"的证据；串号防护目前靠每次切换后的当前用户 ID、顶栏显示名与视图内容断言，没有能真正触发串号的变异证据 |

**边界（须保留）**：
- 只覆盖内联审批列表；底部审批弹层与"全部批准"未覆盖；妈妈作为发行人的界面也没有走。
- 单进程顺序切换账号，不是两台设备同时在线，不覆盖并发审批或实时刷新。
- 越权 403、空原因 422、重复处理 409 的 API 行为不在本测试内（前两者由 `real_backend_b_review_test.dart` 覆盖），本测试只重复 409 重复处理检查。
- SQLite 不是 MySQL；非冷启动、非真机；规则确认（Q-10 等）与人工验收继续独立保留，不由自动化代签。
- 后端"待审就发奖"类变异检查仍未做（可把后端目录指向临时副本，不改原仓库）。

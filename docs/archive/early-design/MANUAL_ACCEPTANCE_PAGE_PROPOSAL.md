# 提案：验收网页内嵌"人工验收指引"（只读展示）

> Codex 于 2026-11-13 已完成技术评审，允许按限定范围实施；本文保留原方案与取舍，最终边界和实施顺序见 [方案评审](../../reviews/MANUAL_ACCEPTANCE_PAGE_REVIEW.md)。尚未实施代码，不构成业务规则或人工验收确认。

日期：2026-11-13。状态：**仅方案，未实施；待 Codex 核对方向，负责人未决定实施。** 起因：负责人看 `/stories#/life-piggy-bank-us23/TASK-A-002` 时发现，登录账号、操作步骤要另外翻 `ACCEPTANCE_GUIDE_BUSINESS.md`，希望验收只聚焦一个页面。

## 1. 目标与边界

做：在每个故事的页面里，直接显示这条故事"人要怎么亲手验收"：准备、账号、步骤、应看到什么、辅助核对。

不做（沿用现有约束）：页面录入/签字；让页面读取验收或规则确认记录；改"人工"一栏的"未验收"语义；迁移目录；审计、CI。页面只展示指引，**展示指引不等于已验收**。

## 2. 现状与问题

- 故事 yaml（`examples/stories/*.story.yaml`）的 `main_flow[].expected` 已经写了"应看到什么"，但**没有**账号、环境、具体点哪里、辅助核对。
- 这些信息只在手册里。手册与页面是两份内容，修改后会不一致。
- 账号、密码实际是 LPB `tools/manual_acceptance/manual_env.sh` 种下的数据，也是第三处。

## 3. 数据放哪里：新增独立的"人工验收指引"文件，不改故事 schema

候选：
- **(a) 扩展故事 schema 加人工字段**：缺点是故事摘要（digest）会因此变化，已有证据与规则确认会被连带判为过期；且"点哪里、用哪个账号"是环境与界面细节，不是需求本身。**不推荐。**
- **(b) 新增 `examples/guides/<story-id>.guide.yaml`，通过故事 ID 关联**（推荐）：不进入故事摘要、不影响证据有效性；按原则 1，它是项目的东西，将来与故事、映射一起随项目走。本次仍和故事、映射一起放在 FlowTree 的 `examples/`，与现状一致，迁移另议。
- (c) 只在页面里写静态文字：就是上次说的方案 B，会形成第二份真相。**不推荐。**

## 4. 指引文件格式（草案，字段尽量少）

```yaml
schema_version: '0.1'
story: TASK-A-002
environment:
  summary: 隔离后端（临时 SQLite，非 MySQL，非真实数据）+ 临时副本客户端
  start:                       # 只给技术同事看，折叠
    - tools/manual_acceptance/manual_env.sh
    - tools/manual_acceptance/manual_client.sh start
  fixture_ref: tools/manual_acceptance/accounts.json   # 见第 5 节
accounts: [solo]               # 引用 fixture 里的账号名，不在这里写密码
steps:
  - for: STEP-01               # 对应故事步骤，页面把它挂在该步骤下
    do: 登录 solo，打开任务页
    see: 有"每日喝水两次"，进度 0/2 次，奖励 +15 A；记下当前 A 积分 P
    if_not: 原样记录看到的内容
  - for: STEP-02
    do: 点"打卡"，在弹出框点"确认提交"
    see: 进度 1/2 次；未显示已完成；A 积分仍是 P
    if_not: 积分变了或显示已完成，记录为不通过
auxiliary:                     # 界面上看不到、由技术同事用后台接口核对的项
  - for: STEP-03
    text: A 流水只多一条 +15，余额与账本一致
    note: 辅助核对，不是你在界面上看到的
```

要点：
- `for` 必须引用故事里真实存在的步骤或分支 ID，缺失或多余由校验报错，避免指引与故事脱节。
- 不再重复"expected"：页面同时显示故事里的 expected（规则）和指引里的 `see`（界面现象），两者各自来源清楚。

## 5. 账号如何与脚本保持一致（只有一份真相）

建议在 LPB 增加一个 `tools/manual_acceptance/accounts.json`（用户名、显示名、角色、预置说明、密码），**`manual_env.sh` 的种子脚本读它，指引页面也读它**。这样脚本改账号，页面自动变。
- 代价：改动 LPB 里已提交且复验过的脚本，需 Codex 重新复验，并使 US-23/US-24 证据再次待更新（`tools/` 参与指纹）。
- 替代（更轻）：账号先写在指引文件里，加一条测试读取 `manual_env.sh` 的种子并比对，不一致就失败。不改 LPB，但仍是"两处声明 + 一致性检查"。
- 我倾向**先用替代方案**，等原则 1 的迁移议题定下来再统一。需要 Codex 取舍。

密码只对隔离环境有效；页面需标明"仅验收用隔离环境"，不应暗示可用于真实账号。

## 6. 页面呈现

在步骤详情抽屉（或步骤卡）里新增"人工验收"区块，使用现有"需要你"的紫色标识：
1. 准备：环境一句话 + 账号表（名字、账号、密码、用在哪）；启动命令默认折叠。
2. 每个步骤下：**你做什么 / 应看到 / 不一致怎么办**。
3. 辅助核对：单独列出并标注"不是你在界面上看到的"。
4. 页面不放任何"通过/不通过"按钮，"人工"一栏维持"未验收"。
5. 没有指引文件的故事：区块不显示，不报错。

## 7. 手册怎么办

- 第一版：手册保留，但在顶部注明"步骤以验收页面为准"，并只保留背景、范围、"证明不了什么"，步骤表删去，避免两份内容。
- 以后：若需要给不开网页的人，可由指引文件生成 Markdown，**不手写**。

## 8. 实施步骤与验证（若方向通过）

1. 新增指引的数据模型与加载（严格字段、`for` 引用校验），单元测试覆盖：引用不存在、重复、缺文件。
2. `view` 接口带出指引；页面渲染区块；页面渲染与接口测试。
3. 为 TASK-A-002、TASK-B-001 写指引（内容来自现有手册，不新增规则）。
4. 一致性检查：指引账号与 `manual_env.sh` 种子比对。
5. 核对：故事摘要、证据有效性不因新增指引而改变（应有专门断言）；桌面、深色、手机宽度截图。
6. 手册瘦身，并注明以页面为准。

## 9. 风险与未决

- 指引属于"人工验收怎么做"，不是规则确认，不能被当作负责人已确认的内容。
- 范围：先只做 US-23、US-24 两条故事；SAV-001、TASK-A-001 暂不做。
- 未决，请 Codex/负责人定：指引文件放 `examples/guides/` 是否合适；账号一致性用"共享 JSON"还是"比对测试"；该功能是否在"暂不继续增加功能"的约束之内。
